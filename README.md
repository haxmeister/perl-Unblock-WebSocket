# Unblock::WebSocket

Platform, framework, and event-loop neutral WebSocket for Perl.

Unblock::WebSocket is a protocol engine. It does not open sockets, perform TLS,
resolve names, create timers, or run an event loop.

Feed an established WebSocket connection bytes:

    $ws->input($bytes_from_transport);

Take generated bytes back out:

    while ($ws->want_write) {
        my $bytes = $ws->output;
        $transport->write($bytes);
    }

Send application messages directly:

    $ws->send_text('hello');
    $ws->send_binary($bytes);
    $ws->ping('probe');
    $ws->close(code => 1000, reason => 'done');

The same engine is intended to work with Linux::Event, IO::Async, AnyEvent,
Mojolicious, blocking sockets, in-memory transports, HTTP/2 streams, HTTP/3
streams, and other ordered byte transports.

## Client and server

An established client endpoint:

    use Unblock::WebSocket::Client;

    my $ws = Unblock::WebSocket::Client->new(
        on_message => sub {
            my ($ws, $payload, $type) = @_;
            ...;
        },
    );

An established server endpoint uses the same byte API:

    use Unblock::WebSocket::Server;

    my $ws = Unblock::WebSocket::Server->new(
        on_message => sub {
            my ($ws, $payload, $type) = @_;
            ...;
        },
    );

The role determines RFC masking direction. Clients mask frames they send;
servers require client frames to be masked and send unmasked frames back.

The native protocol engine is selected automatically when available. For
differential testing and debugging, `backend => 'perl'` selects the portable
reference implementation while keeping the same public API.

## HTTP handshake

`Unblock::WebSocket::Handshake` constructs and validates WebSocket handshakes
using `Uniform::HTTP` objects.

It supports:

- HTTP/1.1 Upgrade;
- HTTP/2 Extended CONNECT;
- HTTP/3 Extended CONNECT.

For example:

    my ($handshake, $request) =
        Unblock::WebSocket::Handshake->client_request(
            'wss://example.com/chat',
            http_version => '2',
            subprotocols => [ 'chat' ],
        );

The caller sends `$request` through its HTTP implementation. WebSocket does not
own that HTTP connection.

## What Unblock::WebSocket owns

- WebSocket framing
- client masking
- fragmentation
- text UTF-8 validation
- Ping and Pong
- Close semantics
- message-size limits
- WebSocket handshake validation
- subprotocol negotiation
- WebSocket extensions

## What it does not own

- sockets
- DNS
- TLS
- event loops
- timers
- HTTP transport
- listeners
- connection pools
- reconnect policy

## Frames and Uniform

WebSocket frames are private wire-protocol machinery and stay in
Unblock::WebSocket. Uniform::HTTP is used for HTTP request and response objects
at the handshake boundary.

Application messages remain lightweight payload/type callback arguments rather
than requiring a new object allocation for every message.

## Performance

The public byte API is not intended to cap performance.

The architecture reserves a private versioned native adapter ABI so an XS
transport can feed borrowed native buffers directly into the native WebSocket
engine and consume native output without an unavoidable intermediate Perl byte
copy.

This is the planned path for Linux::Event::WebSocket to recover the performance
of its current native bq_websocket integration after protocol ownership moves
here.

See `docs/ARCHITECTURE.md` and `docs/PERFORMANCE.md`.

## Current status

Initial development. The portable reference engine and HTTP/1.1, HTTP/2, and
HTTP/3 handshake model are implemented. A vendored bq_websocket native backend
and versioned native adapter ABI are being validated across Linux, macOS, and
Windows. Full Autobahn validation, public-engine/native-backend integration, and
permessage-deflate remain before the first release is considered complete.
